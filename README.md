# نظام مراقبة السائق (DMS)

مشروع **Driver Monitoring System** لاستخراج إشارات قابلة للتفسير من وجه السائق بهدف دراسة حالات الانتباه والنعاس. يعتمد المشروع على الرؤية الحاسوبية وMediaPipe Face Mesh، ولا يتطلب نموذج تصنيف مدرّب في المرحلة الأولى؛ إذ يطبّق قواعد واضحة على قياسات العين والفم.

يدعم المستودع مسارين:

1. **مسار الصور (Phase 1):** معالجة صور مجموعة FL3D، استخراج الميزات، تصنيف الحالة بقواعد، ثم مقارنة النتيجة بالوسوم الحقيقية وإنتاج تقارير تقييم.
2. **مسار الفيديو (Phase 1.5):** معالجة كل إطار في الفيديو وتصدير سلسلة زمنية من الميزات لكل فيديو، لتكون مدخلاً جاهزاً لنموذج زمني في مرحلة لاحقة.

> هذا مشروع بحثي/تعليمي. نتائجه ليست بديلاً عن نظام سلامة معتمد للاستخدام داخل المركبات.

## العلاقة مع تقرير المشروع وحالة التنفيذ

ملف العرض المرافق للمشروع، `DMS_Ahmad_Alhariri.pdf`، يطرح تصوراً لنظام مراقبة سائق زمني قابل للتوسع: **فهم الإطار → اكتشاف الحدث → الاستدلال الزمني → محرك القرار والتنبيه**. هذا المستودع ينفذ طبقات الرؤية واستخراج الميزات، إضافة إلى تصنيف صور مرحلي بالقواعد وتصدير السلاسل الزمنية. أما التحليل الزمني المدرّب والتنبيهات النهائية فما زالا ضمن خارطة الطريق.

| مكوّن الرؤية/التقرير | الحالة في هذا المستودع | ملاحظات دقيقة |
|---|---|---|
| كشف الوجه | منفّذ | MediaPipe هو الخيار الجاهز الافتراضي. يوجد هيكل `RetinaFaceDetector` فقط، لكنه يرمي `NotImplementedError` وليس قابلاً للاستخدام بعد. لا يوجد YOLO Face منفّذ. |
| Face Mesh | منفّذ | MediaPipe Face Mesh، بما يصل إلى 468 نقطة؛ ومع `refine_landmarks` يمكن الاستفادة من نقاط القزحية عند إتاحتها. |
| فهم الإطار | منفّذ | ميزات العين والفم ووضعية الرأس واتجاه النظر والجودة والهندسة. |
| اكتشاف أحداث مثل التثاؤب/انغلاق العين | منفّذ جزئياً | مؤشرات أحادية الإطار وقواعد `EAR` و`MAR` موجودة؛ لا يوجد كاشف حدث زمني مستقل. |
| التصنيف `alert/yawning/microsleep` | منفّذ لمسار الصور | محرّك قواعد قابل للتفسير؛ ليس نموذج تعلم عميق. |
| السلاسل الزمنية للفيديو | منفّذ | تصدير صف لكل إطار بصيغتي Parquet وCSV وملف metadata. |
| PERCLOS، مدة الرمش، معدل الرمش، واتجاهات النافذة الزمنية | غير منفّذ بعد | التقرير يعرضها كإشارات زمنية مقترحة؛ الموجود حالياً هو `blink_proxy` لكل إطار فقط. |
| TCN أو Transformer زمني | غير منفّذ بعد | لا توجد طبقة تدريب أو استدلال أو أوزان نموذج زمني في `src/`. |
| Fatigue Score / Risk Level / Alert System | غير منفّذ بعد | هي مخرجات مستهدفة في التقرير وليست واجهة تشغيل حالية. |
| قدرات إضافية (الهاتف، الحزام، التدخين، التعرّف على السائق) | غير منفّذة | واردة في قابلية التوسع المستقبلية في التقرير. |

بهذا الفصل، يمكن استخدام README كمرجع صادق لما يعمل الآن وكمخطط واضح لما يتبقى للوصول إلى الرؤية الكاملة.

## الفكرة العامة

```text
صورة أو فيديو
      │
      ├── كشف الوجه (MediaPipe؛ واجهة RetinaFace مهيأة للتطوير لاحقاً)
      ├── MediaPipe Face Mesh واستخراج معالم الوجه
      ├── تطبيع المعالم وحساب الميزات الهندسية والفسيولوجية
      │     ├── العين: EAR، انغلاق العين، مؤشّر الرمش
      │     ├── الفم: MAR، الانفتاح، مؤشّر التثاؤب
      │     ├── الرأس: Pitch / Yaw / Roll
      │     ├── النظرة: الاتجاه الأفقي والرأسي
      │     ├── الجودة: الضبابية والإضاءة
      │     └── هندسة الوجه والتناظر
      │
      ├── [الصور فقط] محرّك قواعد: alert / yawning / microsleep
      └── تصدير البيانات والتقارير أو السلاسل الزمنية
```

## حالات السائق

| الحالة | المعنى | منطق التصنيف الافتراضي في مسار الصور |
|---|---|---|
| `alert` | السائق منتبه | الحالة الافتراضية عندما لا تتحقق قواعد النعاس أو التثاؤب |
| `yawning` | تثاؤب | قيمة `mar` أعلى من عتبة `mar_yawning` |
| `microsleep` | نعاس/إغماض قصير للعين | انخفاض `ear_avg` مع إغلاق العينين، أو انخفاض شديد في EAR |

العتبات ليست ثابتة علمياً لكل بيئة؛ يمكن تعديلها في `configs/default.yaml` ويفضل معايرتها على بياناتك.

## المتطلبات

- Python 3.10 أو أحدث
- Windows أو Linux أو macOS
- كاميرا غير مطلوبة: المشروع يعالج ملفات صور وفيديو موجودة مسبقاً
- يوصى ببطاقة NVIDIA/CUDA لمسار الفيديو الطويل، لكن التنفيذ على CPU مدعوم

أهم المكتبات: OpenCV، MediaPipe، NumPy، Pandas، Scikit-learn، PyArrow، Matplotlib وSeaborn. القائمة الكاملة موجودة في `requirements.txt`.

## مسار الصور: FL3D والتصنيف بالقواعد


وتكون الحالات المسموح بها افتراضياً: `alert` و`yawning` و`microsleep`. يستخدم المشروع الوسوم الحقيقية للتقييم فقط، بينما تُستخرج معالم الوجه داخلياً من MediaPipe ولا يعتمد على معالم FL3D الجاهزة.

### تشغيل كامل

```powershell

```

```powershell

```

### تشغيل سريع للتجربة


## مسار الفيديو: استخراج الميزات الزمنية

### شكل مجلدات الفيديو

يكتشف المحمّل الفيديوهات داخل الجذور المحددة في `paths.video_data_roots`. الشكل الشائع هو:

```text
Fold5_part2/
├── 55/
│   ├── 0.mp4
│   ├── 5.mp4
│   └── 10.mp4
└── 56/
    └── ...
```

أسماء مجلدات المشاركين يجب أن تطابق التعبير `^\d+$` افتراضياً. الامتدادات المدعومة في الإعداد الحالي هي `.mov` و`.mp4` و`.avi` و`.mkv`. يمكن وضع `labels.csv` اختيارياً في جذر البيانات (أو المجلد الأب) لربط الفيديوهات بوسوم.

### التشغيل

```powershell
py -m dms.pipeline.video_main --config configs/video_default.yaml
```

أو:

```powershell
dms-video --config configs/video_default.yaml
```

تشغيل محدود للتحقق:

```powershell
py -m dms.pipeline.video_main --config configs/video_default.yaml --max-videos 3
```

### كيف يعمل المسار

- يكتشف الفيديوهات ويرتبها حسب مجلد البيانات والمشارك.
- يقرأ الإطارات تدريجياً، لذلك لا يُحمّل فيديو كامل إلى الذاكرة.
- ينشئ كل عامل (worker) كواشفه وكائنات MediaPipe الخاصة به؛ لا تُشارك هذه الكائنات بين العمليات.
- يعالج كل إطار: كشف وجه ← معالم ← ميزات.
- يسجل الإطارات الفاشلة في الجدول نفسه مع `processing_success=false` وقيم ميزات فارغة (`NaN`) بدلاً من إيقاف الفيديو كله.
- يصدر ملف فشل باسم `<video>_FAILED.json` إن فشلت معالجة فيديو بالكامل، ويكمل بقية الفيديوهات.
- عند تفعيل `skip_existing`، يتجاوز الفيديو الذي لديه ملف Parquet وملف metadata مكتملان.

### المخرجات

لكل فيديو، تُكتب الملفات في المسار التالي:

```text
outputs/temporal_features/<fold>/Subject_<id>/<اسم_الفيديو>.parquet
outputs/temporal_features/<fold>/Subject_<id>/<اسم_الفيديو>.csv
outputs/temporal_features/<fold>/Subject_<id>/<اسم_الفيديو>.meta.json
outputs/temporal_features/<fold>/Subject_<id>/feature_schema.json
```

يحتوي ملف `meta.json` على عدد الإطارات الكلي والمعالَج والناجح والفاشل، دقة الفيديو، FPS، الجهاز المستخدم، وحالة انقطاع القراءة. أما `feature_schema.json` فيحفظ ترتيب الأعمدة وإصدار المخطط (`1.0`).

ويُنشأ ملخص تشغيل عام في:

```text
outputs/video_runs/<timestamp>/config_snapshot.json
outputs/video_runs/<timestamp>/run_summary.json
```

## أعمدة الميزات الزمنية

كل صف يمثل إطار فيديو واحداً. تشمل الأعمدة الوصفية `video_id` و`subject_id` و`fold_name` و`frame_index` و`timestamp_sec` و`fps` و`processing_success`.

| المجموعة | أبرز الميزات |
|---|---|
| العين | `ear_left`, `ear_right`, `ear_avg`, `eye_opening`, `eyes_closed`, `blink_proxy` |
| الفم | `mar`, `mouth_opening`, `mouth_width_norm`, `nose_to_mouth_ratio`, `yawning_indicator` |
| وضعية الرأس | `pitch`, `yaw`, `roll`, `head_pose_valid` |
| اتجاه النظر | `gaze_horizontal`, `gaze_vertical`, `gaze_magnitude`, `gaze_valid` |
| جودة الصورة | `blur`, `brightness`, `detection_confidence`, `face_bbox_area_ratio` |
| هندسة الوجه | `eye_distance`, `eye_distance_norm`, `face_height_ratio`, `face_width_ratio`, `symmetry_score`, `nose_angle`, `vertical_alignment`, `mouth_nose_offset` |

### كيف تُحسب الميزات

| المجموعة | الحساب المنفذ |
|---|---|
| EAR | نسبة المسافات العمودية للعين إلى المسافة الأفقية باستخدام ست نقاط لكل عين: `(\|p2-p6\| + \|p3-p5\|) / (2\|p1-p4\|)`. يحسب المشروع قيمة لكل عين ثم `ear_avg`. |
| انغلاق/رمش العين | `eyes_closed` يساوي 1 عندما تكون `ear_avg` أقل من `ear_blink_threshold`، و`blink_proxy` يساويه في الإطار نفسه. لا توجد تجميعة زمنية للرمش بعد. |
| MAR والتثاؤب | `mar` هو المسافة بين الشفة العليا والسفلى مقسومة على عرض الفم. `yawning_indicator` يساوي 1 عند تجاوز `mar_yawn_threshold`. |
| وضعية الرأس | `cv2.solvePnP` يطابق ست نقاط وجه ثنائية الأبعاد مع نموذج وجه ثلاثي الأبعاد تقريبي، ثم يستخرج `pitch` و`yaw` و`roll`. قيمه تقديرية لأن معاملات الكاميرا مبسطة. |
| اتجاه النظر | يستخدم موضعي القزحية عندما تكون فهارسها متاحة؛ وإلا يستخدم متجه الأنف إلى منتصف العينين كمؤشر تقريبي. لذلك لا يعد بديلاً عن تقدير نظرة مُعاير للكاميرا. |
| الجودة | `blur` هو تباين Laplacian للصورة الرمادية و`brightness` متوسط شدتها مقسوماً على 255. |
| الهندسة والتناظر | تُطبّع قياسات مختلفة بمسافة العينين لتقليل أثر حجم الوجه، وتُحسب درجة التناظر من أزواج معالم معرفة في مخطط MediaPipe. |

### منطق القواعد بالتفصيل

ترتيب الأولوية الافتراضي هو `microsleep` ثم `yawning` ثم `alert`:

```text
إذا ear_avg < ear_microsleep و eyes_closed = 1  → microsleep
وإلا إذا mar > mar_yawning                     → yawning
وإلا إذا ear_avg < eyes_closed_ear              → microsleep
وإلا                                            → alert
```

القيم الابتدائية في `configs/default.yaml` هي `0.20` و`0.55` و`0.21` بالترتيب. يحفظ الكائن الداخلي أيضاً درجات مبسطة لقواعد النعاس والتثاؤب، لكن جدول ميزات الصور يصدّر التسمية المتوقعة أساساً.

## تفاصيل المكوّنات البرمجية

| المسار | المسؤولية |
|---|---|
| `dataset/loader.py` | يقرأ ملفات تعليقات FL3D وينشئ عينات صور، ويتجاهل معالم البيانات الجاهزة لأن الاستخراج يتم من MediaPipe. |
| `dataset/validator.py` و`registry.py` | فحص وجود الصور، توزيع الوسوم/المشاركين/التقسيمات، وفهرسة العينات وتصفيتها. |
| `dataset/video_dataset.py` | اكتشاف الفيديوهات والمشاركين وتحميل `labels.csv` الاختياري. |
| `detectors/` | واجهة موحدة لكاشف الوجه وتنفيذ MediaPipe؛ RetinaFace واجهة مستقبلية غير مكتملة. |
| `landmarks/` | واجهة المعالم، MediaPipe Face Mesh، وتحويل/تطبيع الإحداثيات والهندسة. |
| `features/` | ست حاسبات مستقلة يمكن تعطيل أي منها من الإعداد: `eye`, `mouth`, `head`, `gaze`, `quality`, `geometric`. |
| `rules/engine.py` | تصنيف صور قابل للتفسير بالقواعد والعتبات. |
| `pipeline/runner.py` | السلسلة الكاملة للصور: تحميل، معالجة، تصدير، تقييم، تحليل إخفاقات وEDA ورسوم. |
| `pipeline/frame_processor.py` | معالجة إطار فيديو واحد من دون تصنيفه نهائياً؛ يكتب نتيجة فاشلة آمنة بدلاً من إسقاط السلسلة. |
| `pipeline/video_pipeline.py` | تنسيق تشغيل الفيديو، إنشاء مجلد التشغيل، الملخص، والتنفيذ التسلسلي. |
| `pipeline/video_executor.py` و`video_worker.py` | تشغيل عدة فيديوهات في عمليات مستقلة؛ عدد العمال الفعلي محصور بين 1 و4. |
| `pipeline/video_dashboard.py` و`utils/progress.py` | عرض تقدم الطرفية وFPS ووقت المعالجة وETA واستهلاك CPU/RAM عندما تكون الطرفية تفاعلية. |
| `video/` | قراءة metadata للفيديو وتغذية الإطارات تدريجياً وFace Mesh بوضع التتبع للفيديو. |
| `sequence/` | بناء صفوف مرتبة زمنياً وتصدير CSV/Parquet وmetadata ومخطط الأعمدة. |
| `evaluation/` | Accuracy وPrecision وRecall وMacro-F1 ومصفوفة الالتباس وتحليل الأخطاء. |
| `analysis/` و`visualization/` | إحصاءات وصفية حسب الفئة، Cohen's d وMann-Whitney، ورسوم histogram/scatter/boxplot/correlation/confusion matrix. |
| `utils/` | تحميل/دمج/تحقق إعدادات Pydantic، المسارات، JSON والجداول، التسجيل، والتحقق من CPU/CUDA/MediaPipe delegate. |

### التعامل مع الأخطاء وإعادة التشغيل

- فشل قراءة صورة أو كشف وجه أو استخراج معالم في مسار الصور ينتج عينة بحالة `processing_success=false` بدلاً من إنهاء التشغيل.
- فشل إطار فيديو يظل ممثلاً في التسلسل، مع رسالة في `error_message` وميزات `NaN`، للحفاظ على المحاذاة الزمنية.
- فشل فيديو بالكامل يكتب manifest باسم `<stem>_FAILED.json` ويستمر التنفيذ مع الفيديو التالي.
- التصدير متين لإعادة التشغيل: يتحقق `skip_existing` من ملف Parquet وملف metadata ويعيد استخدام تصدير مكتمل فقط.
- ملف `config_snapshot.json` في كل تشغيل يحفظ الإعداد الفعلي المستخدم لإعادة إنتاج النتائج.

### الأجهزة والتوازي

`compute.device: auto` يتحقق من CUDA عبر PyTorch إن كان مثبتاً أو من OpenCV، ثم يختار `cuda` أو `cpu`. يختار `mediapipe_delegate: auto` وحدة GPU فقط إن كانت MediaPipe Tasks API تدعمها. لا يعني اختيار `cuda` بالضرورة أن جميع عمليات MediaPipe تعمل على GPU؛ سجل التشغيل يوضح الجهاز والـdelegate الفعليين.

في وضع العمال المتعدد، يعالج كل عامل فيديو كاملاً وبترتيب إطاراته، ويملك قارئ الفيديو والكاشف وFace Mesh ومُستخرج الميزات الخاص به. لذلك لا تُشارك كائنات MediaPipe بين العمليات.

### `configs/default.yaml` — الصور

- `paths.data_root`: موقع صور FL3D وملفات التعليقات.
- `dataset.splits`: التقسيمات المطلوب تشغيلها.
- `detector.provider`: `mediapipe` هو المزود الجاهز. قيمة `retinaface` محفوظة كواجهة مستقبلية وليست مفعلة في الإصدار الحالي.
- `features.enabled_groups`: مجموعات الميزات المراد حسابها.
- `rules.thresholds`: عتبات `MAR` و`EAR` للتصنيف القائم على القواعد.
- `evaluation.primary_split`: التقسيم الذي تُحسب عليه المقاييس الأساسية.
- `analysis.generate_plots`: تفعيل أو تعطيل الرسوم.

### `configs/video_default.yaml` — الفيديو

- `paths.video_data_roots`: قائمة مجلدات الفيديو، مثل `Fold5_part2`.
- `paths.temporal_features_dir`: مكان حفظ السلاسل الزمنية.
- `video.export_formats`: صيغ التصدير (`parquet` و`csv`).
- `video.skip_existing`: يمنع إعادة معالجة فيديو مكتمل.
- `video.max_videos`: حد اختياري لعدد الفيديوهات.
- `video.use_video_landmark_tracking`: تفعيل وضع التتبّع الزمني للمعالم.
- `compute.device`: `auto` أو `cpu` أو `cuda`.
- `compute.mediapipe_delegate`: `auto` أو `cpu` أو `gpu`.
- `compute.num_workers`: عدد عمليات معالجة الفيديو المتوازية. ابدأ بـ`1` للتشخيص ثم زد العدد بما يناسب الذاكرة والمعالج.
- `compute.frame_buffer_size`: حجم مخزن قراءة الإطارات.

### مخطط المعالم

ملف `configs/landmarks_mediapipe.yaml` يعرّف فهارس MediaPipe المستخدمة لحساب EAR وMAR ووضعية الرأس واتجاه النظر والتناظر. عند تعديلها، احرص على توافقها مع إصدار MediaPipe Face Mesh ومع تفعيل `refine_landmarks` عند استخدام فهارس القزحية.

## الأداء وحل المشكلات

- جرّب فيديو واحداً أولاً باستخدام `--max-videos 1`.
- إذا ظهرت مشاكل ذاكرة أو أخطاء مرتبطة بـMediaPipe، اجعل `compute.num_workers: 1`.
- إذا لم يُكتشف أي فيديو، راجع `paths.video_data_roots` وامتدادات الفيديو ونمط مجلدات المشاركين.
- إذا كانت نتائج `EAR` أو `MAR` غير مناسبة لبياناتك، عاير `features` و`rules.thresholds` على عينة موسومة.
- قد تختلف سرعة التنفيذ بشدة حسب دقة الفيديو وطوله والجهاز وعدد العمال.
- ملفات الفيديو والـParquet والمخرجات الكبيرة قد لا تكون مناسبة للرفع إلى GitHub. احتفظ بالكود والإعدادات والملفات الصغيرة في المستودع، وضع البيانات والنتائج الضخمة في تخزين خارجي أو Git LFS عند الحاجة.

## التطوير المستقبلي

المسار الزمني مصمم ليكون نقطة انطلاق لمرحلة تعلم آلي لاحقة، مثل LSTM أو GRU أو Transformer زمني. في هذه المرحلة تُستخدم ملفات Parquet لكل فيديو كمدخلات، ثم تُجزّأ إلى نوافذ زمنية وتدرّب على الوسوم المتاحة، مع الحرص على تقسيم التدريب والاختبار حسب المشارك لمنع تسرّب البيانات.

استناداً إلى خارطة الطريق في التقرير، التسلسل المقترح هو:

1. دراسة جودة البيانات وتوزع الوسوم لكل مجموعة ومشارك.
2. تثبيت وتقييم مسار الرؤية الحالي ومعايرة عتباته.
3. تحويل مؤشرات الإطار إلى أحداث زمنية، مثل إغلاق عين مستمر أو رمش طويل أو تثاؤب أو هبوط رأس.
4. بناء نوافذ زمنية ومؤشرات مثل PERCLOS ومعدل الرمش واتجاه الرأس والنظرة.
5. تدريب ومقارنة TCN كنموذج أولي مع Transformer صغير أو بدائل زمنية أخرى.
6. تحويل مخرجات النموذج إلى درجة تعب ومخاطر ومستوى تنبيه قابل للضبط.
7. إضافة وحدات اختيارية مثل كشف استخدام الهاتف أو عدم ربط الحزام، مع الحفاظ على فصلها كوحدات مستقلة.
